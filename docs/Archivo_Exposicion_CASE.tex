	\section*{Resumen}
	El presente informe documenta la aplicación del ciclo completo de \textit{Model-Driven Development} (MDD) sobre un subsistema representativo del Sistema Inteligente de Mantenimiento de Palma Africana (SIMPA), correspondiente al Proyecto Fin de Curso del equipo. Se seleccionó Enterprise Architect como herramienta MDD por su soporte maduro de plantillas de generación de código en C\#/.NET, alineado con la plataforma objetivo del PFC. Se modeló el subsistema de \textit{Monitoreo Fitosanitario y Gestión de Labores Agrícolas}, compuesto por once clases del dominio con relaciones de asociación, composición, agregación y generalización. A partir de dicho modelo se configuró y ejecutó el mecanismo de generación de código, se verificó la compilación y ejecución de una unidad demostrable, y se evidenció el cierre del ciclo mediante una prueba de \textit{roundtrip} controlada. El trabajo se organiza en un repositorio público de GitHub con evidencia de contribución de cada integrante.
	
	\vspace{0.3cm}
	\textbf{Palabras clave:} Model-Driven Development, MDA, UML, Enterprise Architect, generación de código, ingeniería de requisitos.

	% ===================== MARCO TEÓRICO =====================
	\section{Marco teórico}
	
	\subsection{Model-Driven Engineering (MDE), MDA y MDD}
	\textit{Model-Driven Engineering} (MDE) es el paradigma de desarrollo de software en el cual los modelos dejan de ser documentos de apoyo y pasan a constituir artefactos de primera clase del proceso: el modelo se convierte en la fuente autoritativa del sistema, y las implementaciones se derivan de él mediante transformaciones automatizadas \cite{schmidt2006}, \cite{bucchiarone2020}.
	
	\textit{Model-Driven Architecture} (MDA) es la iniciativa del \textit{Object Management Group} (OMG) que estructura el desarrollo en tres niveles de abstracción \cite{omg_mda2014}:
	\begin{itemize}[nosep]
		\item \textbf{CIM} (\textit{Computation Independent Model}): representa el dominio y las reglas de negocio, independiente de cualquier consideración computacional. En el caso del SIMPA corresponde a los procesos agrícolas del cultivo de palma africana.
		\item \textbf{PIM} (\textit{Platform Independent Model}): describe la lógica del sistema sin atarse a una plataforma de despliegue concreta. Corresponde al diagrama de clases de dominio presentado en la Sección \ref{sec:modelo}, previo a la aplicación del perfil C\#/.NET.
		\item \textbf{PSM} (\textit{Platform Specific Model}): el mismo modelo, enriquecido con estereotipos y valores etiquetados específicos de la plataforma objetivo (perfil «Entity» orientado a Entity Framework Core).
	\end{itemize}
	
	\textit{Model-Driven Development} (MDD) es la aplicación práctica de MDE al ciclo de vida del software: los modelos guían la construcción del sistema y el código fuente se obtiene, total o parcialmente, mediante generadores automáticos \cite{selic2003}, \cite{brambilla2017}.
	
	\subsection{Transformaciones M2M y M2T}
	Las transformaciones \textbf{modelo-a-modelo (M2M)} producen un modelo destino a partir de uno de origen, ambos conformes a metamodelos (por ejemplo, PIM $\rightarrow$ PSM). El estándar OMG de referencia es \textit{Query/View/Transformation} (QVT) v1.3 \cite{omg_qvt2016}.
	
	Las transformaciones \textbf{modelo-a-texto (M2T)} producen artefactos textuales —código fuente, configuración, documentación— a partir de un modelo. El estándar OMG de referencia es \textit{MOF Model to Text} (MOFM2T) v1.0 \cite{omg_mofm2t2008}. En este trabajo, Enterprise Architect ejecuta una transformación M2T directa: del modelo de clases PSM se obtiene código fuente C\# mediante sus plantillas de generación internas (\textit{Code Templates}).
	
	\subsection{Metamodelo y perfiles UML}
	Un \textbf{metamodelo} define la sintaxis abstracta de un lenguaje de modelado; UML se define sobre MOF (\textit{Meta Object Facility}) \cite{omg_uml2017}. Los \textbf{perfiles UML} extienden el metamodelo mediante estereotipos, valores etiquetados y restricciones aplicables a un dominio o plataforma concreta. En el modelo del SIMPA se aplicó el estereotipo \texttt{«Entity»} sobre las clases de dominio, de modo que el generador de Enterprise Architect produzca clases persistibles mediante Entity Framework Core.
	
	\subsection{Forward, reverse y round-trip engineering}
	El \textit{forward engineering} consiste en generar código a partir del modelo; el \textit{reverse engineering}, en recuperar el modelo a partir del código; y el \textit{round-trip engineering} mantiene ambas direcciones sincronizadas. Este trabajo demuestra el ciclo \textit{forward} completo y, de forma controlada, un \textit{roundtrip}: un cambio introducido en el modelo se refleja en el código tras la regeneración (Sección \ref{sec:roundtrip}).
	
	\subsection{Estado del arte}
	El campo de las transformaciones de modelos cuenta con más de 60 herramientas catalogadas \cite{kahani2019}, y persisten retos abiertos en escalabilidad, interoperabilidad y adopción industrial \cite{bucchiarone2020}, \cite{whittle2014}.

	\section{Justificación de la selección de la herramienta}
	
	El PFC del equipo (SIMPA) está desarrollado sobre la plataforma \textbf{C\# / .NET}, con persistencia mediante \textbf{Entity Framework Core}. Frente a este requisito se evaluaron tres alternativas:
	
	\begin{center}
		\begin{tabularx}{\textwidth}{lXX}
			\toprule
			\textbf{Herramienta} & \textbf{A favor} & \textbf{En contra (para este PFC)} \\
			\midrule
			\textbf{Enterprise Architect} & Plantillas de generación de código y documentación editables (\textit{Code Templates}), MDG Technology para perfiles personalizados, trazabilidad nativa (\textit{Traceability window}, \textit{Relationship Matrix}). & Curva de aprendizaje inicial en la edición de plantillas. \\
			\\
			StarUML & Generador oficial para C\# vía extensión. & Extensiones de generación menos maduras para personalizar el mapeo de asociaciones a colecciones tipadas. \\
			\\
			Visual Paradigm & \textit{Instant Generator} robusto, plantillas ORM/JPA. & Foco principal en Java/JPA; el soporte de plantillas C\#/EF Core es menos directo que en EA. \\
			\bottomrule
		\end{tabularx}
	\end{center}
	
	Se seleccionó \textbf{Enterprise Architect} por su capacidad de edición fina de plantillas de código y documentación (\textit{Model Report}), su generación directa de código C\# a partir de los diagramas, su soporte de trazabilidad integrada (empleada en la Sección \ref{sec:modelo}) y por ser la herramienta con la que el equipo ya tenía experiencia previa, lo que facilitó el desarrollo de las prácticas sin contratiempos.
	
	% ===================== DESCRIPCIÓN DEL SUBSISTEMA =====================
	\section{Descripción del subsistema del PFC modelado}
	
	El SIMPA es un sistema orientado a la gestión integral del cultivo de palma africana, cuyas funcionalidades principales incluyen: registro de plantaciones y lotes de cultivo; gestión de trabajadores y actividades agrícolas; registro de labores de riego, polinización y control fitosanitario; monitoreo de incidencias en el cultivo; detección de plagas y enfermedades mediante análisis de imágenes; generación de alertas y recomendaciones de tratamiento; predicción de producción y cosecha; y generación de reportes estadísticos e históricos.
	
	Para esta actividad se seleccionó el subsistema de \textbf{Monitoreo Fitosanitario y Gestión de Labores Agrícolas}, por ser representativo del núcleo funcional del PFC y por integrar en un solo flujo el registro de labores agrícolas, la detección de plagas mediante análisis de imágenes y la generación de alertas con recomendaciones de tratamiento — cubriendo así una porción no trivial y demostrable del sistema completo.
	
	\textbf{Actores principales:} agrónomo/supervisor de campo, trabajador agrícola, módulo de análisis de imágenes (servicio de IA del SIMPA).
	
	\textbf{Requisitos funcionales cubiertos por el subsistema modelado:}
	\begin{itemize}[nosep]
		\item RF-1: Registrar plantaciones y sus lotes de cultivo asociados.
		\item RF-2: Registrar labores agrícolas (riego, polinización, control fitosanitario) por lote y trabajador.
		\item RF-3: Registrar incidencias detectadas en un lote.
		\item RF-4: Asociar a una incidencia una detección de plaga obtenida por análisis de imágenes.
		\item RF-5: Generar alertas a partir de una detección de plaga.
		\item RF-6: Emitir recomendaciones de tratamiento asociadas a una alerta.
	\end{itemize}

	\section{Configuración del generador}
	
	\begin{itemize}[nosep]
		\item \textbf{Generador utilizado:} plantilla nativa de Enterprise Architect para C\#, personalizada mediante el editor de \textit{Code Templates}.
		\item \textbf{Versión de Enterprise Architect:} 17.1.1716.
		\item \textbf{Lenguaje/framework objetivo:} C\# 12 / .NET 8, Entity Framework Core 8.
		\item \textbf{Parámetros de generación:} directorio de salida \texttt{generado/Modelos/}; convención de nombres PascalCase para clases y propiedades; anotación \texttt{[Key]} sobre el atributo \texttt{id} de cada clase «Entity».
		\item \textbf{Decisiones de mapeo documentadas:}
		\begin{itemize}[nosep]
			\item Asociación 1 a * $\rightarrow$ propiedad \texttt{public ICollection<T> Nombre \{ get; set; \}}.
			\item Generalización UML $\rightarrow$ herencia de clases C\# (\texttt{class LaborRiego : LaborAgricola}).
			\item Atributos tipados UML \texttt{Date} $\rightarrow$ \texttt{DateTime} de C\#.
		\end{itemize}
	\end{itemize}

	\subsection{Limitaciones observadas del generador}
	\begin{itemize}[nosep]
		\item El generador no produce las capas de \textit{Service} ni \textit{Controller}; estas se completan manualmente y se distinguen del código generado mediante su ubicación en carpetas separadas (\texttt{generado/Servicios}, \texttt{generado/Controllers}).
		\item Las validaciones de negocio (por ejemplo, rangos válidos de \texttt{dosis\_Litro}) no se generan automáticamente y deben añadirse a mano sobre las clases parciales o en la capa de servicio.
		\item El generador no crea automáticamente las migraciones de Entity Framework Core; estas se generan aparte con \texttt{dotnet ef migrations add}.
	\end{itemize}

	% ===================== CONCLUSIONES =====================
	\section{Conclusiones}
	
	\begin{itemize}[nosep]
		\item La aplicación del ciclo MDD sobre el subsistema de Monitoreo Fitosanitario del SIMPA permitió reducir el trabajo manual de codificación de las clases de dominio, delegando en Enterprise Architect la generación de las propiedades, tipos y relaciones estructurales.
		\item La edición de las plantillas de código (\textit{Code Templates}) resultó indispensable para que el mapeo de asociaciones y tipos fuera coherente con las convenciones de Entity Framework Core, en lugar de depender únicamente de la plantilla C\# genérica.
		\item El generador no reemplaza el diseño de las capas de servicio y controladores, que continúan siendo responsabilidad del equipo; el valor de MDD radica en la generación confiable y trazable de la capa de datos, no en la automatización total del sistema.
		\item La prueba de \textit{roundtrip} evidenció que el modelo puede evolucionar de forma segura sin perder el código manual, siempre que la política de regeneración aísle claramente las carpetas generadas de las escritas a mano.
	\end{itemize}
